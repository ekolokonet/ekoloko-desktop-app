# יעדי יציבות, תמיכה ושחזור

המסמך מרכז את הבעיות שעלו אצל משתמשי macOS, מה כלול באפליקציה בגרסה
`1.0.28`, ומה עדיין דורש טיפול בצד האתר או השרת.

## סטטוס היעדים

### הושלם באפליקציית הדסקטופ

- **זיהוי גרסה בצילום מסך:** הגרסה מוצגת באופן קבוע כתגית בסרגל העליון,
  כשכבה קטנה מעל אזור המשחק (גם במסך מלא), בכותרת החלון ובחלון About של
  macOS.
- **תיקון התחברות ללא התקנה מחדש:** הכפתור `תקן התחברות` מנקה, לאחר אישור,
  את מטמון HTTP, כל ה-cookies והאחסון המקומי, מטמון אימות HTTP, מטמון DNS
  ונתוני Pepper Flash המקומיים. לאחר מכן נטען מסך הכניסה מחדש.
- **איפוס מלא במקום App Cleaner:** בתפריט macOS:
  `ekoloko > איפוס מלא לפני הסרה…`. הפעולה מוחקת לאחר יציאת האפליקציה את
  תיקיות Application Support, Caches, Preferences, Saved Application State,
  HTTPStorages ו-WebKit השייכות רק ל-ekoloko.
- **לוג רשת שימושי לתמיכה:** הלוג מתעד קוד HTTP, סוג משאב, טעינה מהמטמון,
  זמן, Content-Type, גודל, ETag ומצב Cloudflare לכל asset חשוב ולכל כשל.
  query strings, cookies, request headers ותוכן התגובה אינם נשמרים בלוג.
- **מצב ריצה בחבילת הלוגים:** `שמירת לוגים` כוללת גרסת אפליקציה, מערכת
  הפעלה, גודל מטמון, מספר cookies רלוונטיים, proxy, נוכחות Flash, מצב
  online/offline, נוכחות אלמנט Flash וסמני האחסון של תהליך ההתחברות.
- **שגיאות TLS:** כשל תעודה נרשם עם URL מצונזר ונדחה במפורש; האפליקציה לא
  עוקפת תעודות לא תקינות ולא משאירה בקשת תעודה תלויה.
- **מניעת גל טעינות כפול:** גרסה `1.0.22` חוסמת באפליקציית הדסקטופ את
  `preload_assets.js` הישן של האתר. המשחק ממשיך לטעון את המשאבים הנדרשים
  בעצמו, בלי סבב preload מקביל שמעמיס במיוחד לאחר ניקוי מטמון.
- **Discord Rich Presence:** גרסה `1.0.27` מציגה פעילות משחק ב-Discord
  דרך ה-socket המקומי גם ב-macOS. ברירת המחדל אנונימית; שם המשתמש והמיקום
  מוצגים רק לאחר בחירה מפורשת בכפתור הפרטיות שבסרגל.

### דורש שינוי בצד האתר/שרת

בקובץ החי `https://play.ekoloko.org/ekoloko/preload_assets.js` קיימות כמה
בעיות שיכולות ליצור דיווח שגוי כאילו assets נטענו:

1. בדיקת היכולת `'link' in document.createElement('link')` אינה בדיקה תקינה
   ל-preload/prefetch ולכן המסלול שנבחר אינו אמין.
2. במסלול XHR, אירוע `load` נחשב הצלחה בלי לבדוק status, Content-Type או
   גודל תגובה. גם `404` יכול להירשם כ-`Loaded`.
3. כל promise נכשל נתפס בתוך `catch`, ולכן `Promise.all` מסתיים בהצלחה
   ומודפס `Critical assets loaded` גם כשאחד או יותר נכשלו.
4. הסמן `ekoloko_assets_preloaded` נכתב מיד, לפני סיום ההורדות וללא תלות
   בתוצאה. לקוח שכשל באמצע עדיין מסומן כ-cached למשך 24 שעות.
5. הדף עושה preload ל-`shell.swf`, אבל המשחק נטען דרך
   `shell.swf?version=<random>`. כתובת אקראית בכל פתיחה יוצרת cache key חדש,
   כך שה-preload עלול לא לשמש את הבקשה האמיתית והמטמון של 24 שעות נעקף.
6. Cloudflare מנסה להזריק `static.cloudflareinsights.com/beacon.min.js`, אך
   ה-CSP של הדף מאפשר scripts רק מ-`self`. לכן בכל פתיחה נרשמת שגיאת CSP
   ידועה. היא אינה כשל SWF, אך כדאי לבטל את ההזרקה או להתאים במכוון את ה-CSP
   כדי שלא תסתיר שגיאות אמיתיות בלוג.

התיקון המומלץ בצד האתר:

- להשתמש בגרסת build קבועה, למשל `shell.swf?v=2026.07.24.1`, ולהחליף אותה
  רק כאשר ה-SWF משתנה.
- לטעון ב-preload את אותה כתובת מדויקת שה-embed יטען.
- לקבל הצלחה רק עבור `status` בטווח `200–299`, Content-Type צפוי וגודל
  מינימלי סביר.
- לכתוב את סמן ה-preload רק לאחר שכל ה-assets הקריטיים הצליחו.
- לדווח בנפרד את שם ה-asset, status, ETag, cache hit/miss וזמן הטעינה.

## נוהל תמיכה קצר

1. בקשו צילום מסך. ודאו שהתגית `v1.0.28` נראית בסרגל העליון.
2. בקשו ללחוץ `שמירת לוגים` **לפני** איפוס, כדי לשמור את הכשל המקורי.
3. חפשו בלוג:
   - `network ... status=4xx/5xx` — השרת/CDN החזיר שגיאה.
   - `network ... request failed error=...` — DNS, TLS, proxy או ניתוק.
   - `cache=true` יחד עם ETag ישן — חשד ל-asset ישן מהמטמון.
   - `contentType` שאינו מתאים או `bytes=?/0` — תגובה לא תקינה אף ש-status
     עשוי להיות `200`.
   - `plugin-crashed` — כשל Pepper Flash ולא כשל asset רגיל.
   - `network-state offline` — מערכת ההפעלה דיווחה על אובדן רשת.
   - `browserDiagnosticFailure` — כשל שתועד בתהליך ההתחברות שבדף.
4. בקשו ללחוץ `תקן התחברות`, לאשר ולהתחבר מחדש.
5. אם הבעיה חוזרת מיד, שמרו לוג נוסף והשוו URL, status, ETag, proxy וגודל
   בין הלוג שלפני האיפוס ללוג שאחריו.
6. רק אם האפליקציה עצמה פגומה או מיועדת להסרה, השתמשו ב-
   `ekoloko > איפוס מלא לפני הסרה…`, ורק לאחר שהאפליקציה נסגרת העבירו את
   `ekoloko.app` לפח.

## בדיקת בסיס שבוצעה

ב-24 ביולי 2026 נבדקו מבחוץ דף הכניסה ושבעת ה-assets שמופיעים ב-preloader:
`shell.swf`, `login.swf`, `main.swf`, `only_machine.swf`, `register.swf`,
`avatarGender.swf` ו-`linkme.swf`. כולם החזירו באותה בדיקה `HTTP 200`,
Content-Type של Flash ותוכן שאינו ריק; גם תעודת TLS של `play.ekoloko.org`
הייתה תקינה. Smoke test מתוך Electron 8 הארוז קיבל את אותם assets, עם ETag,
וטען את מסך הכניסה.

הבדיקה מוכיחה שה-assets הקריטיים היו זמינים בזמן הבדיקה, אך אינה שוללת כשל
ללקוח מסוים, cache/CDN שונה, proxy, ניתוק באמצע תגובה או asset נוסף שנטען
מאוחר יותר מתוך ה-SWF. זו הסיבה שהלוג החדש מתעד את מה שהלקוח עצמו קיבל ולא
מסתפק בבדיקת שרת חיצונית.

ב-smoke test של חבילת `1.0.22` עם פרופיל נקי, דף הכניסה ו-Flash נטענו
בהצלחה והחסימה של `preload_assets.js` נרשמה בלוג. באותה בדיקה התגלו גם
שני קבצים שמחזירים `404` אמיתי מהשרת:
`/ekoloko/items/MKP/MKP_1.swf` ו-`/ekoloko/items/MKP/MKP_2.swf`.
404 כזה אינו תקלה זמנית ולכן מנגנון ה-retry החדש אינו חוזר עליו; יש לתקן
את הנתיב/הנתונים או להעלות את הקבצים בצד השרת.

ב-30 ביולי 2026 חבילת `1.0.27` עברה קומפילציה ואריזת ZIP/DMG ב-macOS.
גרסת ה-bundle וה-DMG אומתה כ-`1.0.27`, תוסף Flash וארכיטקטורת x64 נמצאו
בחבילה, וחיבור Discord המקומי השלים handshake וקיבל אישור ל-SET_ACTIVITY.

## אם האפליקציה כבר הועברה לפח

macOS אינו מפעיל uninstaller כאשר גוררים קובץ `.app` לפח. לכן אין לאפליקציה
הזדמנות למחוק נתונים לאחר שכבר הוסרה. ניתן לפתוח ב-Finder את התיקיות הבאות
ולהעביר לפח **רק** פריטים בשם המצוין:

- `~/Library/Application Support/`:
  `ekoloko-rewritten` וגם `ekoloko` אם קיימת תיקייה ישנה.
- `~/Library/Caches/`:
  `org.ekoloko`, `ekoloko` או `ekoloko-rewritten`.
- `~/Library/Preferences/`:
  `org.ekoloko.plist`.
- `~/Library/Saved Application State/`:
  `org.ekoloko.savedState`.
- `~/Library/HTTPStorages/`:
  `org.ekoloko`.
- `~/Library/WebKit/`:
  `org.ekoloko`.

אין למחוק תיקיות Macromedia/Flash כלליות: הן עלולות להשתייך לתוכנות אחרות.
נתוני ה-Flash של הגרסה המצורפת ל-ekoloko נמצאים בתוך תיקיית Application
Support של האפליקציה ונמחקים באיפוס המובנה.

## מגבלות וסיכונים שנותרו

- גרסת macOS אינה מתעדכנת אוטומטית כרגע, מפני שה-build אינו חתום ו-
  Squirrel.Mac אינו מחיל עדכון על bundle לא חתום. יש להפיץ DMG חדש ולוודא
  שהלקוח אכן עבר לגרסה המוצגת.
- Electron `8.2.0` ו-Pepper Flash הם רכיבים ישנים. שדרוג Electron רגיל אינו
  טריוויאלי, מפני שגרסאות Chromium חדשות הסירו Flash. בטווח הארוך נדרש מסלול
  מעבר מה-Flash או runtime מבודד ומתוחזק; בטווח הקצר יש לשמור בדיקות macOS
  עבור TLS, proxy, GPU וטעינת SWF בכל release.
- לוג HTTP של Electron אינו בהכרח רואה socket גולמי שה-SWF פותח לשרת המשחק.
  אירועי login/server-list מתוך ה-SWF צריכים להמשיך להישלח דרך
  `ekolokoBrowserReportEvent`, כדי להבחין בין כשל asset לבין כשל חיבור לשרת
  המשחק.
